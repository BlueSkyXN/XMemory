# XMemory 整理

从未处理的事件和必要证据维护当前认识与可复用记忆。除配置由设置维护外，整理是唯一修改已有文件的动作，所以要先读后写、逐项交代去向，不把所有工作结果都升级成长期规则。

先读 [共同约定](./references/contract.md) 和 [文件格式](./references/storage.md)。提炼经验时读 [经验判断](./references/experience.md)；更正或忘记时读 [更正与撤回](./references/corrections.md)。

## 1. 确认方式和范围

- **手动整理**：用户当轮要求整理、更正、忘记或合并。可以做判断类改动，但只改要求的范围。
- **定时整理**：由定时提示词或其他无人值守方式调用。只做记账类改动；判断类改动写进近况的“待确认建议”。
- 只检查或只提建议时完全只读。

记账类：追加当日文件、重写近况、移入或移出积压、把新记忆收进入口、核对已声明的替代关系后标“已替代”并更新必要元信息。判断类：合并、改写或删除记忆正文，晋升经验或常驻条目，到期复查，撤回。涉及替代声明时也读 [更正与撤回](./references/corrections.md)，不把状态更新扩大为正文合并。

只整理指定的个人或项目范围，不顺手改其他项目；外部维护项目交还原维护者。用户配置了同步命令时，开始前先同步；同一时间只在一处整理，发现另一处正在整理的迹象就停下说明。

## 2. 找出要处理的内容

读取配置、目标入口、`CURRENT.md`、`BACKLOG.md` 和 `WITHDRAWN.md`。只在指定范围列出各月事件文件，与该范围所有当日文件“处理的事件”中的明确引用核对，再排除明确撤回的内容；链接按所在文件目录解析，不只匹配短名，其他段落提及不算处理。不按记录年龄或上次整理时间排除事件，因为别处离线写下的事件可能晚到。

近 30 天只作为正文阅读优先级，也优先展开与当前任务相关的旧事件。先比较清单和登记，不一次加载所有事件正文，不扫描其他项目或原生来源。用户明确限定时间窗时遵守并说明边界。未能全部处理、登记不可读或核对不全时，报告剩余范围与缺口，不宣称全部完成或“本次无变化”。

另外检查：`notes/` 中还没被入口收录的新记忆；声明了 `supersedes` 的新记忆；`review` 已到期的记忆；同步工具留下的冲突副本（文件名带 conflicted、副本编号等）。

主动采集新来源只在用户同时要求或核实具体缺口时进行，不把整理变成全源盘点。

## 3. 决定每条内容的去向

- 当前状态变化：更新近况，并在当日文件记下状态变化。
- 仍有效：保留，必要时完善条件与来源。
- 重复：合并到已有稳定 ID，不换个标题新增一条。
- 有稳定复用价值：创建或更新记忆。
- 来源不足或互相矛盾：在近况中标为待确认并写明双方依据，不静默择一。
- 无关、噪声或敏感内容：不收录，在当日文件中列为已处理、无需跟进。
- 已被替代或要求撤回：只对同范围、目标明确、无冲突且已生效的 `supersedes` 标“已替代”；其余列为待确认，不改旧正文。撤回按更正规则处理。

用户直接表达的要求可以证明其偏好和决定；代码、测试或实际结果用于证明执行行为。助手说“已完成”不是完成的充分证据。定时整理遇到判断类去向时，只把建议和依据写进“待确认建议”。

## 4. 重写近况

把 `CURRENT.md` 当一份简短、可重写的交接，按工作线分节，不是日志；不规定重写比例。逐项核对旧待办：保留、完成、取消、被替代、移入积压或待确认。每条旧待办要么还在新近况里，要么在当日文件的“状态变化”中写明去向和依据。没有近期消息不能当作完成，也不能通过缩小原目标宣称完成。

连续 3 次成功记入当日文件的整理都没有新依据的待办移入 `BACKLOG.md`（按 [积压模板](./templates/BACKLOG.md)），近况只留数量和指向；有了新依据再移回。失败重试、残缺登记和无变化零写入不累计次数，数不清时保留并说明。写明截至时间和本次实际读过、未读的来源。个人近况只概述跨项目重点并链接项目近况。

待确认建议保留原事件或记忆地址，重写时逐项保留未处理的旧建议。接受、驳回、撤销或被替代时，在当日文件记下去向和依据；不能因本轮没提到而删除。重试按原地址核对并补充，不重复新建建议。建议保存成功可作为来源事件的处理结果，不表示建议已获准执行。

## 5. 准备当日登记

按 [当日文件模板](./templates/day.md) 准备今天 `records/YYYY-MM/YYYY-MM-DD.md` 的新节：处理的事件、决定与冲突、状态变化。此时只准备内容，按第 7 步最后写入。每个事件一行，含明确相对链接及已保存的去向：更新近况、形成记忆、登记待确认建议或无需收录。“已处理”不代表业务完成或事实已核实。没有实际结果或状态变化时不生成空节；读取失败可以零写入并报告缺口，不能回复“本次无变化”。

## 6. 维护记忆和入口

围绕稳定主题，一条记忆一个主张，保留适用条件、来源、已知例外和确认时间。经验说明在什么条件下采取什么处理、实际结果和边界；一次反馈先是案例，没有验证就标记待确认。已有正式规范或业务 Skill 时，只保留入口和有价值的例外，不复制规范，也不自动编辑 Skill。

入口 `MEMORY.md`：`## Index` 上方只放每次会话都需要的少数一行条目；索引每条写主题、一句结论或何时读取，用相对链接，只指向真实存在的文件。从项目推广到个人跨项目约定，需要明确的适用性和用户授权；推广到团队或组织还需要维护主体、审阅与访问规则，本插件不提供。

## 7. 写入顺序与校验

按顺序写：记忆、积压、撤回墓碑 → 近况和入口 → 回读确认 → 当日文件。只改发生变化的文件；每个文件写前读取并确认未被他人修改，不用旧稿覆盖新内容。入口只链接已存在的目标，新当日文件通过日期目录查找，不提前加入入口。

必要文件持续冲突、写入失败或回读不符时，停止当前个人／项目范围的后续写入，不把尚未完成的事件登记为已处理。保留已成功保存的内容，报告完成部分与未完成部分，不回滚他人的新内容。根配置无效、库不可达或另一处正在整理同一范围时，在写入前停止相关整理。

重试先按事件地址、记忆 ID、行动 key 核对已有结果，只补缺失步骤；已有记忆、待办、建议不重复创建。结果已保存而当日文件没写成功时，回读确认后补登记。若当日文件只追加了一部分，核对完整登记、补缺失条目，残缺条目不作处理凭据，不重复完整条目。记录处理结果不等于重新执行事件中描述的部署等业务动作。

所有本次结果确认后，在当日文件末尾追加新节并回读确认；文件不存在才新建，不修改已有的完整节。只有确认结果已保存的事件进入“处理的事件”。当日文件仍失败时报告登记未完成，下次继续核对补齐。

冲突副本：当日文件的两节都保留；其他文件合并后删除副本，删除前需用户确认（定时整理只把它列入待确认建议）。

完成后检查：旧待办和待确认建议都有去向、链接有效、ID 稳定、状态和来源完整、当日登记与实际结果一致。用一个实际后续问题试查：能否找到当前答案、截至时间、依据和不确定性？用户配置了同步命令时，结束后再同步一次；同步失败只报告本地已保存、同步未完成，不重做已完成的整理或声称其他机器已更新。

## 完成

说明认识有什么变化、处理了哪些事件、哪些待办状态变了、哪些判断类改动在等确认，以及具体入口、剩余事件和读取缺口。核对完整且无实质变化时零写入，定时整理回复“本次无变化”；失败、未读或尚有未处理事件时报告实际边界。整理完成不等于模型已训练、准确率提升或企业验收通过。
