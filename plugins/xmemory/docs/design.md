# 设计：XMemory 1.4

## 为什么重做

1.0–1.3 是“纯技能”实现：清单计数、进度游标、项目归属、日期分桶、时间戳、批次状态都写在规则里，由模型照做。真实回填暴露了三类问题：

- 机械工作交给模型会出错：编造时间戳、漏读大来源、计数自相矛盾，而且每修一次就多一段规则；
- 输入是二手的：各客户端原生记忆已经是别人的总结，再总结一次只会更弱，按证据规则也只能全部标“待确认”；
- 读取侧没有接通：除了一个客户端，其他客户端根本不知道记忆库存在。

1.4 参照 Codex 原生记忆的做法重做：确定性代码负责所有机械工作，模型只做两步语义工作，而且只从一手会话提取。

## 流水线

```text
scan        读取器列出会话 → 代码判定项目、按本地日期切分 → 生成提取任务（带内容指纹）
import      Codex 已有逐会话记忆只读导入；Office Memory 逐字转录
next/submit 执行技能的代理领取任务 → 读输入 → 写 JSON → 运行时校验、脱敏、写入会话摘要并提交 git
consolidate 单写者：加锁 → 列出本范围新增/修改/删除的输入 → 代理更新产物 → 运行时校验、写时间、生成时间线、提交 git
```

### 提取（Phase 1）

- 单位是“会话 × 本地日期”，超长再分部分。日期由代码从消息时间按配置时区换算，跨天会话自然拆开。
- 输入只含用户和助手的可见消息，工具内容截断；系统注入、隐藏推理不进入输入。
- 输出固定三字段 JSON：`slug`、`summary`（会话摘要）、`raw_memory`（给整合用的要点）。三字段都为空表示不值得记。
- 会话 ID、项目、时间窗、来源路径、提取时间与执行客户端全部由运行时写进 frontmatter，模型不写元数据。
- 会话后来又有新消息时，指纹变化，任务重新进入待处理；重新提取的摘要覆盖旧摘要，整合时作为“修改”处理。
- 提取方法参照 Codex 的提取提示词：以减少用户纠正为目标、用户消息优先、助手提议不算结论、保留原话。

### 整合（Phase 2）

- 全局一把整合锁（带租约，过期自动释放）；多个客户端可以同时提取，但同一时间只有一处整合。
- `begin` 列出本范围所有新增、修改、删除的输入，全文附在输入文件里；没有变化就直接返回。
- 代理只能改本范围的产物和 `memory_summary.md`。`finish` 时运行时检查：没有越界改动、意识五节齐全、旧待处理项都有着落、链接有效、没有疑似密钥。通过后写入时间戳、生成时间线、提交 git；失败就列出原因，可修正后重试或 `abort` 回到整合前。
- 删除的输入（如 `forget`）在整合时传播：只删除仅由它支撑的内容。

## 库结构

见 `skills/xmemory/references/layout.md`。要点：

- `sessions/` 是逐会话摘要（提取产物），`inbox/` 是当场笔记，两者都是整合的输入；
- `projects/<项目>/` 下的 `AWARENESS.md`（当前状态）、`MEMORY.md`（任务组手册）、`topics/`（有稳定 key 的条目）、`daily/`（叙述，可选）是整合产物，`timeline/` 由代码生成；
- `memory_summary.md` 是全局入口；
- `.xmemory/state.sqlite` 保存会话清单、任务、租约、锁和输入登记，不进 git，可重建；
- 整个记忆根是 git 仓库，每次提取、导入、整合都是一个提交，可以回看和回滚。

## 技能划分

一个工具、多个技能：运行时 CLI 只有一份（`skills/xmemory/scripts/`），各技能只描述什么时候用、怎么用它。

| 技能 | 职责 |
|---|---|
| `xmemory` | 工具本体：命令总表、共同规则、库结构 |
| `xmemory-recall` | 查阅（只读），`session` 命令回到原会话 |
| `xmemory-note` | 当场记一条 |
| `xmemory-run` | 运行一轮：提取 + 整合 + 校验 |
| `xmemory-extract` | 清点、导入、逐会话提取 |
| `xmemory-consolidate` | 单写者整合 |
| `xmemory-setup` | 建库、项目、导入、告知、定时提示词 |
| `xmemory-maintain` | 状态、检查、忘记、中断处理 |

技能之间通过相对路径引用同一插件里的 `xmemory` 技能，因此安装时要保留整个 `skills/` 目录。

## 读取

不注入、不强制。各客户端的用户级规则文件里放一段告知（`notice` 生成），说明记忆库在哪、什么情况值得查、怎么查；由 AI 自己决定是否使用。查阅方法参照 Codex：先看全局摘要和项目意识，再按关键词 grep 手册，一般 4–6 步内结束；会漂移的事实按“漂移风险 × 核实成本”决定是否现场核实。

## 调度

没有后台进程。需要定期运行时，用客户端自己的自动化功能（如 Codex 自动化、ZCode 定时任务）挂一条固定提示词，由那个客户端的代理按技能执行一轮。

## 与原生记忆的关系

- Codex：只读导入其逐会话记忆（`rollout_summaries/` 与 `raw_memories.md`），不写 Codex 的记忆目录。
- 其他客户端的原生记忆（主题文件、日记）不导入：它们是同一批会话的二手总结。需要时可作为调取线索。
- Office Memory：用 `import office-memory` 逐字转录，正文不改写。

## 边界

- 1.4 只支持单机。
- 会话正文由执行技能的客户端所用模型处理；可用 `[restrict]` 按来源限制，默认不限制。
- 不修改任何客户端的原生数据；不保存原始会话副本、密钥、令牌；遗忘只覆盖本库，不能删除客户端原件或外部备份。
- 运行时校验的是结构、指针、时间和待办着落；语义是否准确要靠评测和人工抽查。
