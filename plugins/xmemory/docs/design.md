# 设计：XMemory 1.4

## 为什么重做

1.0–1.3 是“纯技能”实现：清单计数、进度游标、项目归属、日期分桶、时间戳、批次状态都写在规则里，由模型照做。真实回填暴露了三类问题：

- 机械工作交给模型会出错：编造时间戳、漏读大来源、计数自相矛盾，而且每修一次就多一段规则；
- 输入是二手的：各客户端原生记忆已经是别人的总结，再总结一次只会更弱，按证据规则也只能全部标“待确认”；
- 读取侧没有接通：除了一个客户端，其他客户端根本不知道记忆库存在。

1.4 参照 Codex 原生记忆的做法重做：确定性代码负责所有机械工作，模型只做两步语义工作，而且只从一手会话提取。

## 流水线

```text
scan        读取器列出会话 → 代码判定项目、按本地日期切分 → 生成提取任务（带内容指纹）
import      Codex 已有逐会话记忆只读导入；Office Memory 逐字转录
next/submit 执行技能的代理领取任务（带租约）→ 读输入 → 写 JSON → 运行时核对租约、校验、脱敏、写入会话摘要
consolidate 单写者：加锁、留产物副本 → 列出本范围新增/修改/删除的输入 → 代理更新产物 → 运行时校验、写时间、生成时间线、记整合账本
```

### 提取（Phase 1）

- 单位是“会话 × 本地日期”，超长再分部分。日期由代码从消息时间按配置时区换算，跨天会话自然拆开。
- 输入只含用户和助手的可见消息，工具内容截断；系统注入、隐藏推理不进入输入。
- 输出固定三字段 JSON：`slug`、`summary`（会话摘要）、`raw_memory`（给整合用的要点）。三字段都为空表示不值得记。
- 会话 ID、项目、时间窗、来源路径、提取时间与执行客户端全部由运行时写进 frontmatter，模型不写元数据。
- 会话后来又有新消息时，指纹变化，任务重新进入待处理；重新提取的摘要覆盖旧摘要，整合时作为“修改”处理。
- 读取器跳过了内容（带警告）时只做加法：新增分段、内容增长的分段重新提取；不作废分段、不删除或替换已有摘要。新出现的读取问题让游标失效，下次重读；同样的问题再次出现才推进游标。
- 扫描记录每个会话已覆盖的窗口起点；扩大 `backfill_days` 或 `--days` 时，已扫描过的会话也会补切更早的日期。
- 只有当前租约的领取者能提交或放回。放回或租约过期都计一次失败，满三次转为 `failed`，用 `retry` 或 `skip` 处理。
- 提取方法参照 Codex 的提取提示词：以减少用户纠正为目标、用户消息优先、助手提议不算结论、保留原话。

### 整合（Phase 2）

- 全局一把整合锁（带租约，过期自动释放）；多个客户端可以同时提取，但同一时间只有一处整合。
- `begin` 列出本范围所有新增、修改、删除的输入，全文附在输入文件里；没有变化就直接返回。
- `begin` 记下全库的内容指纹，并给本范围产物留一份副本。代理只能改本范围的产物和 `memory_summary.md`。`finish` 时运行时对比指纹：本范围以外的变化必须是运行时自己写的（例如整合期间别处的提取、forget），否则算越界；再检查意识五节齐全、旧待处理项都有着落、链接有效、没有疑似密钥。通过后写入时间戳、生成时间线、记整合账本；失败就列出原因，可修正后重试或 `abort` 用副本恢复到整合前。整合中断且租约过期时，下一次 `begin` 自动恢复。
- 删除的输入（如 `forget`、会话内容变化后作废的分段）与新增、修改共用同一个待整合条件，在整合时传播：只删除仅由它支撑的内容。整合期间被删除的输入，会在下一轮作为删除再传播一次。

## 库结构

见 `skills/xmemory/references/layout.md`。要点：

- `sessions/` 是逐会话摘要（提取产物），`inbox/` 是当场笔记，两者都是整合的输入；
- `projects/<项目>/` 下的 `AWARENESS.md`（当前状态）、`MEMORY.md`（任务组手册）、`topics/`（有稳定 key 的条目）、`daily/`（叙述，可选）是整合产物，`timeline/` 由代码生成；
- `memory_summary.md` 是全局入口；
- `ledger/` 保存不能丢的状态：撤回记录、各范围已整合的输入版本、写入代数；
- `.xmemory/state.sqlite` 保存会话清单、任务、租约、锁和输入登记，可以用 `rebuild` 从记忆文件和 `ledger/` 重建。

## 状态与恢复

不依赖 git。状态分三层：

| 层 | 内容 | 存放 | 丢失后 |
|---|---|---|---|
| 事实 | 会话摘要、笔记、产物；撤回记录；各范围已整合的输入版本 | 记忆文件与 `ledger/` | 不允许丢，随记忆根备份 |
| 可重建的登记 | 输入登记、已完成的提取任务（摘要 frontmatter 带任务与指纹） | 状态库 | `rebuild` |
| 协调状态 | 待处理任务、租约、失败次数、整合锁、扫描游标 | 状态库 | 重新 `scan`；结果为空的任务会再提取一次 |

每个写命令是一个写事务：持有状态库写锁；改文件前先把 `ledger/state.json` 的写入代数加一，文件原子替换，最后状态库记下同一代数。失败时当场按文件对账；进程被杀则两边代数不一致，下一个写命令先对账。对账只前滚：已写出的摘要登记为完成，撤回账本里的会话补删，重复摘要移到 `.xmemory/recovered/`。状态库缺失或库标识不一致时，所有命令拒绝运行并提示 `rebuild`，不会悄悄建一个空库。

被恢复或覆盖的旧版本放在 `.xmemory/recovered/`，保留 14 天。需要长期历史时，用户可以用任何方式备份记忆根（包括自建 git 仓库）；运行时不依赖也不操作这些工具。

## 技能划分

一个工具、多个技能：运行时 CLI 只有一份（`skills/xmemory/scripts/`），各技能只描述什么时候用、怎么用它。

| 技能 | 职责 |
|---|---|
| `xmemory` | 工具本体：命令总表、共同规则、库结构 |
| `xmemory-recall` | 查阅（只读），`session` 命令回到原会话 |
| `xmemory-note` | 当场记一条 |
| `xmemory-run` | 运行一轮：提取 + 整合 + 校验 |
| `xmemory-extract` | 清点、导入、逐会话提取 |
| `xmemory-consolidate` | 单写者整合 |
| `xmemory-setup` | 建库、项目、导入、告知、定时提示词 |
| `xmemory-maintain` | 状态、检查、忘记、中断处理 |

技能之间通过相对路径引用同一插件里的 `xmemory` 技能，因此安装时要保留整个 `skills/` 目录。

## 读取

不注入、不强制。各客户端的用户级规则文件里放一段告知（`notice` 生成），说明记忆库在哪、什么情况值得查、怎么查；由 AI 自己决定是否使用。查阅方法参照 Codex：先看全局摘要和项目意识，再按关键词 grep 手册，一般 4–6 步内结束；会漂移的事实按“漂移风险 × 核实成本”决定是否现场核实。

## 调度

没有后台进程。需要定期运行时，用客户端自己的自动化功能（如 Codex 自动化、ZCode 定时任务）挂一条固定提示词，由那个客户端的代理按技能执行一轮。

## 与原生记忆的关系

- Codex：只读导入其逐会话记忆，不写 Codex 的记忆目录。Codex 有两版记忆，可能同时在写：V1 在 `~/.codex/memories`（`rollout_summaries/` 加 `raw_memories.md` 原始记忆块），V2 在 `~/.codex/memories_v2`（只有逐会话摘要，超过约 9000 字节从中间截断）。两个根都读；同一会话取较新的快照，同一快照优先 V1。导入的摘要标明来源版本、是否被截断。根缺失、文件格式认不出、V1 明显停更、出现本版不认识的新版本目录时，导入结果和 `status` 都会告警，不会悄悄变少。
- Codex 只处理部分会话（默认近 10 天、闲置 6 小时以上、每次启动最多 2 个），两版都没有的会话本版不自行提取，只报告缺口。Codex 按保留上限删除旧摘要不影响已导入的副本。
- 其他客户端的原生记忆（主题文件、日记）不导入：它们是同一批会话的二手总结。需要时可作为调取线索。
- Office Memory：用 `import office-memory` 逐字转录，正文不改写。

## 边界

- 1.4 只支持单机。
- 会话正文由执行技能的客户端所用模型处理；可用 `[restrict]` 按来源限制，默认不限制。
- 不修改任何客户端的原生数据；不保存原始会话副本（提取任务的输入在任务结束后删除）、密钥、令牌；遗忘只覆盖本库，不能删除客户端原件或外部备份。
- 运行时校验的是结构、指针、时间和待办着落；语义是否准确要靠评测和人工抽查。
