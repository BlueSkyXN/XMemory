# 设计：跨客户端的记忆中心

本文是 1.2.0 设计。文件格式名仍为 `xmemory/v1`：1.1.x 的布局没有投入长期使用，直接按本文重新定义。宿主安装、试运行和多设备效果尚未验收，验证记录见源码仓库 `docs/validation.md`。

## 定位

XMemory 是用户级的集中记忆中心。它让现有 AI 客户端代表用户做三件事：

- **采集**：从各客户端的原生记忆和具体对话中，抽取有用的变化，写成带来源的足迹。
- **整理**：把足迹加工成意识、主记忆、主题、每日记忆和画像。
- **调取**：任何客户端、任何项目，先读常驻层，再按需展开，最后回原件。

它是 AI 级的抽取、整理和加工，不是简单聚合，也不复制原文：原件留在原处，XMemory 保存总结和索引，并告诉 AI 去哪里找原件。

插件只有技能和文档：没有运行期脚本、数据库、MCP、Hook 程序、后台服务或额外模型 API。执行靠宿主已有的读、搜、写和 shell 工具；何时运行由读取协议、Hook 和用户挂的定时任务决定。

## 一条流水线

各家产品的记忆机制，其实都在跑同一条流水线：

```text
原件 → 捕获/提取 → 短期层 → 整理 → 长期层 → 小容量常驻 + 按需检索
```

| 产品 | 捕获 | 短期层 | 整理 | 常驻 |
|---|---|---|---|---|
| Codex | 新回合开始时，后台处理过去已闲置的会话 | 逐会话摘要 | 单任务合并，有冷却 | 紧凑摘要 |
| ZCode、Claude Code、Qoder | 成功回合后提取 | — | 提示词去重；部分有 Dream | 索引 |
| QoderWork | 回合结束，按得分门控 | 按会话分块的日记 | 定期反思，带备份与淘汰 | 正文、画像、最近日记 |
| OpenClaw | 写工具、重置钩子、压缩前写日记 | 按日日记 | 定时 Dreaming，晋升有门槛 | 画像、正文、最近日记 |

各产品的差别只在于：谁触发、短期层是否落盘、整理有没有门槛。它们都只记自己客户端的东西。

XMemory 用技能实现这整条流水线，并覆盖所有客户端：

| 环节 | XMemory |
|---|---|
| 捕获 | 记录（对话中实时）+ 采集（定时或手动） |
| 短期层 | `daily/<日期>/` 足迹 |
| 整理 | 单写者整理 |
| 长期层 | 主题、主记忆、画像 |
| 常驻 | 画像、意识、主记忆要点 |

## 结构

```text
~/.agents/memory/
├── config.toml                        配置：项目、来源、时区、记录策略
├── USER.md                            用户画像
├── AWARENESS.md                       意识
├── MEMORY.md                          主记忆：要点 + 主题索引 + 项目入口
├── topics/<主题>.md                   主题记忆：主记忆的子文件
├── daily/YYYY-MM-DD.md                每日记忆：当天概要
├── daily/YYYY-MM-DD/HHMM-<短名>-<随机>.md   足迹
├── projects/<项目名>/                 项目记忆，结构同上（没有 USER.md）
└── state/                             工作状态（调取时不读）
    ├── sources.md                     来源进度
    ├── runs/                          采集清单
    ├── curation/                      整理记录
    ├── history/                       意识重写前的副本
    └── withdrawn.md                   撤回标识
```

| 层 | 文件 | 回答什么 | 何时读 |
|---|---|---|---|
| 常驻层 | `USER.md`、`AWARENESS.md`、`MEMORY.md` | 我是谁；现在该知道什么、该做什么、什么没定；有哪些长期结论 | 会话开始 |
| 主题与每日层 | `topics/`、`daily/<日期>.md`、`projects/<项目名>/` | 某主题的稳定知识；某天发生了什么 | 按需；延续任务时读最近两天 |
| 足迹层 | `daily/<日期>/*.md` | 那次发生了什么，原件在哪 | 需要细节时 |
| 原件 | 各客户端原生记忆、会话、工作区 | 原话和原始证据 | 需要依据时 |

### 命名

名字尽量和各端的通行叫法一致：

| 文件或目录 | 各端同类叫法 |
|---|---|
| `MEMORY.md` | 各端通用 |
| `USER.md` | QoderWork、OpenClaw、Hermes |
| `AWARENESS.md` | QoderWork 的 awareness |
| `topics/` | Claude Code、ZCode 的主题文件（topic files） |
| `daily/YYYY-MM-DD.md` | QoderWork、OpenClaw、WorkBuddy 的按日文件 |
| `state/` | 各端用隐藏文件或数据库保存的工作状态；这里改用 Markdown，人可以看，也能用 rg 检查 |

### 两条轴

- **项目轴**：`projects/<项目名>/`。项目名等于平台项目根目录名，原样保留，同时登记各客户端对该项目的别名（ZCode 的 slug、Claude 和 Qoder 的路径编码、Codex 的 cwd）。会话按工作目录归属；worktree 归到主仓库。
- **时间轴**：每日记忆按工作日期；足迹按事件发生时间放进当天目录。“总结的”（当天概要）和“详细的”（当天足迹）并排存放。

## 关键设计

### 常驻层小，详情按需

各产品的常驻内容都只有几千到两万多字符：Codex 摘要约 2500 tokens，ZCode 和 Claude 的索引 200 行，QoderWork 正文 10 KiB 加画像 4 KiB。

XMemory 的上限是：画像 4 KiB、意识 16 KiB、主记忆 200 行、每日记忆 12 KiB。记忆是资料，不是指令。

### 主记忆是要点层

`MEMORY.md` 每个主题写一行要点（结论 + 适用条件），并链接 `topics/` 子文件。要点等于主题的 `description`，冲突时以主题文件为准，由整理修正。

### 意识大幅重写，但不丢事

- `AWARENESS.md` 固定五节：当前认识、近期变化、冲突与未知、待处理、记忆候选。
- 每次整理整篇重写，近期优先，常规改写幅度 30%–70%。
- 重写前存副本；重写后比对，改写比例写进整理记录：低于 30% 查漏读，高于 70% 逐项核对待处理。
- 条目可标重要度，超过容量时按“低 → 普通”、同级最老的先移出，并写明去向；关键条目要用户确认才移出；不静默截断。

### 采集：原生记忆优先，会话补缺口

- 各端原生记忆已经提炼过，密度高、成本低，先读。
- 会话按工作目录归项目，只处理已静默的（默认 60 分钟）。
- 一个会话一份足迹，长会话按天拆；不跨会话、跨周按主题合并。

### 整理：一处单写，晋升有门槛

- 整理是唯一修改记忆正文的动作。
- 进入主记忆需要满足其一：用户原话、两条独立证据、执行结果；晋升前要回原件核对。
- XMemory 自己生成的内容不算证据；AI 的结论不能记成用户决定。
- 写后核对三项：关键信息保全、已有条目损失、日期绝对化。

### 用清单保证确定性

| 要保证的事 | 做法 |
|---|---|
| 覆盖 | 每批采集先写清单，一行一项，从列表输出逐项抄录。状态为已提取、无可记内容、跳过、失败四种；没有空状态行才算完成 |
| 进度 | 来源进度只推进到最后一个已完成项 |
| 地址 | 只从读取结果复制，不截断 |
| 日期 | 按配置时区换算；读取工具的时间参数带时区 |
| 未整理内容 | 当天目录中有、当天概要“已吸收足迹”里没列出的足迹，即为未整理 |

## 运行方式

日常有三条线：

1. **实时**：读取协议 + 记录技能。在被纠正、做决定、阶段交接时写足迹。可选接 Hook：会话开始、压缩前、会话结束。
2. **后台**：在任一客户端挂定时提示词，例如每天一次增量采集，再做一次整理。效果相当于一个覆盖所有客户端的后台记忆进程。
3. **首次回填**：按首次回填提示词手动分批执行。

客户端内置的记忆（如 Codex 的后台记忆、QoderWork 的反思）照常运行，XMemory 把它们的产物当作输入，不干预它们。

## 相对 Office Memory 的改进

Office Memory 是此前的自有实践：单个项目内的“日期记录 + 当前认知 + 长期条目”，配有证据分级、候选处置和轮转副本。XMemory 继承它的整理判断，但不是它的翻版：

| 方面 | Office Memory | XMemory 1.2.0 |
|---|---|---|
| 范围 | 一个项目，结果存在项目目录 | 用户级集中库，覆盖 personal 和全部项目；项目按平台项目根目录自动发现并登记各客户端别名 |
| 来源 | 登记的原生来源，按需挑选少量材料 | 各客户端原生记忆的读取映射（同名不同义、归属、可信度、增量），加会话和工作区；原生记忆优先 |
| 短期层 | 只有日期记录，事件当天整理当天写 | 足迹按事件发生日期落盘，一会话一份，带规范地址；历史回填写到真实日期 |
| 覆盖与进度 | 依靠每次挑选的材料，没有逐项清单 | 采集清单逐项登记状态，来源进度只在成功后推进；首次回填有分批流程与验收 |
| 长期层 | 单个长期文件，按 key 维护，逼近体量上限 | 主记忆要点（常驻）+ 主题子文件（按需），可无限拆分 |
| 意识 | 五节，按需重写 | 五节 + 工作线分组；每次整篇重写，30%–70% 自检；按重要度淘汰并记录去向 |
| 画像 | 无 | `USER.md`，跨项目的工作偏好 |
| 晋升 | 证据分级与处置 | 加上多信号门槛、回原件核对、自产内容不算证据、AI 结论不得记为用户决定 |
| 写后核对 | 校验与快照比对（依赖辅助脚本） | 关键信息保全、已有条目损失、日期绝对化三项，纯技能可执行 |
| 运行 | 明确请求时手动整理 | 实时记录、Hook、定时后台采集与整理、首次回填四种方式 |
| 调取 | 读取协议定向读项目文件 | 常驻层 → 最近两天每日记忆 → 主题 → 足迹 → 原件，任何客户端同一读法 |

## 写入规则

- 记录和采集只新建足迹；采集另外只改本批清单和来源进度。
- 整理按“主题 → 主记忆、画像、意识 → 每日记忆 → 回读核对 → 整理记录 → 来源进度”的顺序写。
- 定时整理不合并、改写或删除主题正文，只写进意识的“记忆候选”。
- 失败时停止当前范围，不登记未完成的足迹；重试只补缺失步骤。

## 纯技能的边界

- 不能自己定时或常驻：触发靠宿主的定时任务、Hook 或手动。
- 没有锁和事务：并发靠约定，即采集只新建、整理单写。
- 没有使用次数统计：改用复查日期和近期度。
- 没有向量检索：用宿主的 rg 和文件读取。
- 效果依赖模型遵守规则：每个技能都有强制核对步骤，完成汇报必须附核对结果。

## 研究与正式产品的关系

本设计依据对 Codex、ZCode、Claude Code、Qoder、QoderWork、WorkBuddy、Trae、OpenClaw、Hermes、腾讯与阿里记忆服务的静态研究，以及对本机各端记忆数据的只读核对。借鉴的是机制和教训，不是各产品的私有格式或运行期能力；不宣称与任何产品或草案格式兼容。产品借鉴细节见 [设计来源](design-sources.md)，原始需求对照见 [需求覆盖](requirements.md)。
