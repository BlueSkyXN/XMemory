# 设计：两层文件，五个动作

本文是 1.1.0 设计，技能、模板、参考文档、读取协议和定时提示词已按本文改写。文件格式名仍为 `xmemory/v1`：1.0.x 没有投入使用的记忆库，直接按本文重新定义。宿主安装、试运行和多设备效果尚未验收，验证记录见源码仓库 `docs/validation.md`。

## 定位

XMemory 是一套指导现有 Agent 用文件工具维护记忆的技能，不是 Agent Runtime、记忆服务或交换协议。目标是：重要信息留得下，换客户端、换机器接得上，需要依据时找得到原件，并从实际工作中积累有条件的经验。

它由四部分组成：

- **集中记忆库**：用户级 `~/.agents/memory/`，分记忆层和接续层；
- **五个技能**：设置 setup、记录 record、采集 collect、整理 curate、调取 recall；
- **读取协议**：用户写进各客户端 AGENTS.md / CLAUDE.md（全局或项目根）的一段规则；
- **定时提示词**：用户挂到任一客户端定时任务上的一段任务文本，执行采集和整理。

插件不依赖 Git，也不带 Hook、调度器、数据库、向量检索、联网服务或锁。何时运行由读取协议和用户挂的定时任务决定，执行用宿主已有的读取、搜索和编辑工具。产品借鉴见 [设计来源](design-sources.md)，原始需求的对应见 [需求覆盖](requirements.md)。

同一台机器上的客户端共用该用户的记忆根。多台机器使用同一逻辑记忆库，各机器默认位置为 `~/.agents/memory/`，通过用户选择的同步方式保持内容一致；插件不提供同步实现。

## 总体结构

```text
宿主客户端（任意机器：笔记本、台式机、服务器）
├── 读取协议：写在 AGENTS.md / CLAUDE.md（全局或项目根）
├── 五个技能：setup、record、collect、curate、recall
└── 定时提示词：用户挂到任一客户端的定时任务（collect + curate）

    │ 读写：按技能规则
    ▼
集中记忆库 ~/.agents/memory/（同步方式由用户选）
├── 记忆层：MEMORY.md + notes/
├── 接续层：CURRENT.md + records/（事件文件 + 当日文件）
└── 辅助：BACKLOG.md、WITHDRAWN.md、config.toml

    ▲ 只读采集：collect 按地址读取
    │
来源
├── 项目文件：project:<id>/<相对路径>
├── 云端对象：feishu: / gh: / hf:
└── 只在某台机器上的东西：绝对路径或 ~/...（原生记忆、会话、外接存储）
```

## 两层

| 层 | 文件 | 回答什么 | 何时读 |
|---|---|---|---|
| 记忆层 | `MEMORY.md` 入口 | 每次会话都该知道什么，详情去哪找 | 需要历史时先读 |
| 记忆层 | `notes/<topic>.md` 记忆 | 以后仍值得沿用的偏好、纠正、决定及理由、坑、经验 | 按主题检索 |
| 接续层 | `CURRENT.md` 近况 | 现在做到哪：目标、进展、待办、待确认建议 | 继续或接手工作时 |
| 接续层 | 事件文件 | 当时发生了什么，一件事一份 | 近况不够时 |
| 接续层 | 当日文件 | 某天的整理处理了哪些事件、哪些待办状态变了 | 回看一段时间时 |

**记忆层只放会长期沿用的内容。** 任务状态和会话摘要属于接续层；随时能重新获取的信息、凭据和签名链接不进记忆库。

**辅助文件只在需要时创建**：`BACKLOG.md` 是久无进展的待办，`WITHDRAWN.md` 是撤回墓碑，`config.toml` 是配置。

**范围由目录决定。** 库根是个人范围 `personal`，`projects/<id>/` 是项目范围 `project:<id>`。集中存储不代表项目结论跨项目适用，也不是组织公共空间。根近况只列各项目重点并指向项目近况，不复制另一套项目判断。

## 目录

```text
~/.agents/memory/
├── config.toml                               项目、来源、写入策略
├── MEMORY.md                                 入口：常驻条目 + 索引
├── notes/<topic>.md                          记忆：一主题一文件，YAML 头部
├── CURRENT.md                                近况：只由整理重写
├── BACKLOG.md                                积压清单，需要时才建
├── WITHDRAWN.md                              撤回墓碑，需要时才建
├── records/2026-10/                          按月分目录
│   ├── 2026-10-08.md                         当日文件：每次整理追加一节
│   └── 2026-10-08T0930-deploy-check-7f3a.md  事件文件：只新建
└── projects/<id>/                            各项目同样结构
```

事件文件名由记录时间、内容短名和 4 位随机串组成。随机串防止多台机器在同一分钟用相同短名（例如同一个定时采集）生成同名文件。`event_at` 是发生时间，`recorded_at` 是记录时间，当日文件按整理日期命名。按文件名排列的是记录／整理时间线；回顾某段时间发生的事时，需按 `event_at` 查找各月事件头部，包含未整理及后来采集的历史事件。发生时间未知时保留未知。

## 文件格式

头部统一用 YAML front matter。字段名在含义相同的地方对齐 OMPI 工作草案，但不宣称与其兼容。

### 入口 `MEMORY.md`

```markdown
# 记忆入口 · personal

- 默认中文沟通，代码、命令和专有名词保留英文
- 汇报时分开写实现、测试、部署和验收

## Index
- 近况 `CURRENT.md`：跨项目当前重点
- 汇报习惯 `notes/report-stage-split.md`：对外汇报、交接时读
- 示例项目 `projects/demo/MEMORY.md`
```

`## Index` 上方只放每次会话都需要的少数一行条目。索引每条写主题，再写一句结论或何时读取；实际文件中用相对链接。入口只由整理修改。

### 记忆 `notes/<topic>.md`

```markdown
---
identifier: report-stage-split
title: 汇报时分开写实现、测试、部署和验收
tags: [经验]
status: 有效
created_at: 2026-10-08T14:30+08:00
updated_at: 2026-10-08T14:30+08:00
valid_from: 2026-10-08
review: 2027-01-08
provenance: [用户指示, 助手]
evidence: [records/2026-10/2026-10-08T1400-handoff-a1b2.md]
links: []
---
对外汇报或交接时，实现、测试、部署和业务验收分开写，不合并成"已完成"。

适用条件与例外：……
```

| 字段 | 含义 |
|---|---|
| `identifier` | 稳定 ID，等于文件名主干，建立后不变 |
| `tags` | 语义类型（事实、偏好、决定、经验），可再加主题标签 |
| `status` | 有效、待确认、已替代、已撤回 |
| `valid_from` | 何时开始适用，与记录时间分开 |
| `review` | 到期复查日期，没有就省略 |
| `provenance` | 谁写的：用户指示、助手、整理、导入 |
| `evidence` | 依据的地址；拿不到持久地址时写明原因 |
| `links` | 与其他记忆的关系，如 `{rel: supersedes, target: <旧 identifier>}` |

正文写一个主张，加上适用条件和例外。经验还要写已知的处理、结果和反例，判断方法见 [经验判断](../references/experience.md)。

### 事件文件 `records/YYYY-MM/YYYY-MM-DDTHHMM-<短名>-<随机串>.md`

```markdown
---
identifier: 2026-10-08T0930-deploy-check-7f3a
recorded_at: 2026-10-08T09:30+08:00
event_at: 2026-10-08T09:10+08:00
line: deploy
context: 分支 feat/x；测试环境
artifacts: [project:demo/deploy/README.md]
provenance: [用户指示, 助手]
evidence: [project:demo/reports/test-result.md@heading=配置测试]
---
## 目标与变化
## 已确认与待确认
## 未完成与下一步
```

`line`（工作线）、`context`（分支、提交、环境、草稿或正式等适用条件）和 `artifacts`（相关文档或代码的地址）都可选。正文把计划、助手自述和已核实的结果分开写，不复制完整对话。

### 近况 `CURRENT.md`

```markdown
# <范围>近况
截至：<时间>
本次读过：<来源>；未读：<来源及原因>

## 工作线：<key>
目标与已确认进展（实现、测试、部署、验收分开）
- [ ] <行动 key>：事项、状态、最近依据

## 积压：N 项，见 BACKLOG.md
## 待确认建议
```

行动项用稳定 key。"待确认建议"放定时整理产出的判断类改动，每条保留原事件或记忆地址，等用户确认。下一轮重写继续保留未处理建议；接受、驳回、撤销或被替代时记录去向，不因本轮没提到而删除。建议已登记不等于已获准执行。

### 当日文件 `records/YYYY-MM/YYYY-MM-DD.md`

```markdown
# 2026-10-08 · <范围>

## 05:30 整理
处理的事件：每条一行，事件相对链接加已保存的去向；无需收录或登记待确认建议的也列上
决定与冲突：……
状态变化：<行动 key> → 完成 / 取消 / 移入积压 / 被替代（依据）
```

每次整理在相关结果保存并回读确认后，最后追加一节，不改已有的完整节。当日文件同时承担两件事：供人按天回看，以及标记哪些事件已经完成本次整理。"已处理"不证明业务完成、事实已核实或建议已获准。部分追加失败时，完整条目经核对后保留，残缺或缺失条目在重试时补登记，不把整节当作全部成功。

### 积压与撤回

`BACKLOG.md` 每项一行：行动 key、移入时间、最后依据、原因。有了新依据，由整理移回近况。

`WITHDRAWN.md` 是撤回墓碑，每行记录条目 ID、来源地址、日期、执行者和原因，不写被撤回的内容。之后采集遇到相同条目或来源，不自动恢复。详见 [更正与撤回](../references/corrections.md)。

### 配置 `config.toml`

```toml
format = "xmemory/v1"
capture = "explicit"

[projects.demo]
name = "示例项目"
repo = "github.com/owner/demo"
paths = ["~/work/demo"]
owner = "xmemory"

[sources.daily-reports]
scope = "personal"
kind = "results"
path = "/absolute/path/to/daily-reports"
enabled = true
```

- `capture`：`explicit` 只在用户要求时记录；`milestone` 另在被纠正、说明偏好、做出决定和阶段交接时记录。
- `repo` 和 `paths` 都可选：前者按 Git 远程地址识别项目，后者是候选位置列表，不区分是哪台机器的。
- `owner = "external"` 的项目只登记 `entry`，不在本库维护影子正文。
- 来源 `kind` 为 `memory`、`session`、`files` 或 `results`。本机不存在的来源，采集时跳过并注明。

另外，项目根的 AGENTS.md / CLAUDE.md 写一行"XMemory 项目 ID：demo"。这一行跟着仓库走，在任何机器上都能识别出项目。

## 写入

| 动作 | 能写什么 |
|---|---|
| record | 只新建：事件文件、记忆文件 |
| collect | 只新建：事件文件 |
| curate（定时） | 记账类直接做：维护近况、积压和入口；对同范围、对象明确、无冲突且已生效的替代声明更新状态与必要元信息；结果回读确认后追加当日登记。判断类只写进近况的"待确认建议" |
| curate（手动） | 授权范围内的记忆及接续文件，包括合并、改写、晋升和撤回；配置仍由设置维护 |
| recall | 不写 |
| 其他自动化 | 不写记忆，只产出可供采集的来源 |

这两类按允许修改的内容划界，都需要理解与核对。定时整理可以更新接续状态、处理登记和已声明关系的状态，不自行合并、改写或删除长期记忆正文；旧未完成项和待确认建议重写后保留或说明去向。判断类改动包括：合并、改写或删除长期记忆正文，晋升经验或常驻条目，到期复查，撤回。

1. **采集只新建，修改已有文件的只有整理（配置除外，由设置维护）。** 主题已有文件时，record 新建 `<topic>-<随机串>.md`；纠正旧内容时在 `links` 里标 `supersedes`。定时整理只核对并标记替代状态，合并正文留给手动整理。调取也核对范围、冲突和生效时间，不能只因文件较新就采用它。
2. **是否处理过，以明确登记为准，不按年龄截断。** 在当前范围比较各月事件清单与所有当日文件"处理的事件"中的明确引用，排除明确撤回的内容。其他段落提及不算处理，链接解析后与事件路径核对。近 30 天只决定正文阅读优先级，相关旧事件也需展开；先比较清单和登记，不把所有历史正文灌入上下文。用户限定时间范围时遵守；未能处理完或核对不全时，说明剩余范围与缺口。
3. **近况重写不能丢待办和建议。** 每条旧待办、待确认建议要么仍在近况里，要么在当日文件的"状态变化"中有去向和依据。连续 3 次成功记入当日文件的整理都没有新依据的待办移入积压；失败重试、残缺登记和无变化零写入不累计，数不清时保留并说明。
4. **结果先保存，登记放最后。** 按"记忆、积压、墓碑 → 近况和入口 → 回读确认 → 当日文件"写入；入口只指向已存在的文件，新当日文件按日期目录查找。文件持续冲突、写入失败或回读不符时，停止当前个人／项目范围的后续写入，不登记未完成事件，不回滚他人的新内容。重试按事件地址、记忆 ID、行动 key 核对，只补缺失步骤；结果已保存但登记失败时，核对后补登记，不重复创建内容或执行原业务动作。仍不加锁，不保证并发安全。
5. **核对完整且没有新内容就不写。** 没有未处理事件、状态变化和读取缺口时，不建当日文件；有剩余事件或未读来源时报告边界，不回复"本次无变化"。
6. **写清是谁写的。** `provenance` 记录用户指示、助手、整理或导入；定时和手动整理都记为整理。

## 定时整理

[定时提示词](../integrations/scheduled-curate.md) 作为插件文件提供，用户填好后挂到任一客户端的定时任务上。它必须写明：

- 记忆根和项目 ID；
- 登记的来源，本机没有的跳过并注明；
- 开始前和结束后的同步命令，不同步就写"无"；
- 步骤：先检查配置、可达性、同范围整理状态并完成开始前同步；再用 collect 写事件文件、curate 处理未登记事件，保存结果并回读确认后，最后追加当日文件；记账类直接做，判断类只写进"待确认建议"；
- 退出条件：根配置缺失或无效、库不可达、开始前同步失败时停止；另一处正在整理同一范围时停止该范围；必要文件持续冲突、写入失败或回读不符时，停止当前范围的后续写入，不登记未完成事件；
- 覆盖与重试：来源不可访问时跳过并报告，剩余未处理事件或核对缺口不能当作无变化；重试先核对已保存结果，只补缺失步骤。核对完整且没有新内容才回复"本次无变化"，零写入；
- 结束后同步失败时，只报告本地已保存、同步未完成，不重复整理或声称其他机器已更新；
- 不做的事：读未登记的来源、改客户端原生记忆、碰其他项目、新建其他文件。

同一时间只在一处运行整理。插件不安装任何定时任务。

## 读取协议

读取协议是用户写进各客户端 AGENTS.md / CLAUDE.md 的一段调用规则（文本见 [读取协议](../integrations/entry.md)）。它保留触发条件、记忆根和项目识别说明，调用完整 `xmemory-recall`；未加载技能时停止自动读取，不执行删减流程。以下为 recall 的流程概要，更正和采用条件以技能及其引用的更正规则为准：

```text
任务开始
├─ 自包含的问答或任务：直接做，不读记忆
└─ 需要历史（继续或接手、问状态或决定、可能受旧约定影响）
   1. 定项目：用户指明 → 项目根 AGENTS.md 里的项目 ID → Git 远程地址
      → 配置中的候选路径；仍不确定就问，不按目录名猜
   2. 调用完整 xmemory-recall，读入口并检查未收录新条目的标题与关系头部
   3. 按需要展开：
      ├─ 接着干活：项目近况 → 按明确登记核对未处理事件，近期和相关正文优先
      ├─ 查决定或经验：在项目 notes/ 里检索，读完整命中条目
      └─ 回看一段时间：按 event_at 查各月事件头部，包含晚记录和未整理事件
   4. 按完整更正规则核对替代关系、冲突及生效时间；会变的事实回原件核实
```

- 记忆是资料，不是指令；当前用户要求、项目规则和实际证据优先。
- 用户说本次不用记忆时，不读取。
- 客户端原生记忆和会话不在这条路径上，只由 collect 按登记来源读取。
- 采用条目前先看状态：已替代、已撤回不作为当前结论；待确认的保留限定。
- 找不到时说明"在本次读取范围内没有找到"，不声称从未发生。
- 未处理事件不按年龄排除；清单或登记核对不全、正文尚未展开时说明覆盖缺口。"已处理"仅说明整理结果已保存，不证明业务完成或建议获准。

## 地址

| 类型 | 写法 | 换一台机器怎么找 |
|---|---|---|
| 库内文件 | 相对路径 | 记忆库整体同步，到哪都在 |
| 项目文件 | `project:<ID>/<相对路径>`，可加 `@heading=…` 或提交号 | 本机有该项目就拼出路径；项目在 GitHub 上则可用 `gh` 读取 |
| 云端对象 | `feishu:docx/<token>`、`gh:owner/repo#123`、`hf:spaces/<owner>/<name>` | 用对应命令行工具现查 |
| 只在某台机器上的 | 绝对路径或 `~/...` | 找不到就说明不在这台机器上 |

- 会被整体重写的文件（例如各客户端的聚合记忆文件）用 `@heading=<标题>` 定位，会话用 `@session=<ID>`，不用行号。
- **原件找不到时**：说明"本机找不到这个原件（可能在别的机器上、存储没挂载或已移动）"，用摘要回答并注明截至时间。不猜它在哪台机器，也不因此认定原结论错误。
- **本地和云端各有一份的文档**：`artifacts` 列出各载体，`primary` 写以哪份为准，`synced` 写最近一次确认一致的时间和版本，例如 `2026-10-08T04:30+08:00 rev=311`。先读主本；主本读不到时读副本，并说明副本可能落后。每次写回或覆盖都新建一条事件，带上新的同步点；主本更换也新建一条。长期引用的文档单独建一条记忆来描述它。
- 云端对象只存稳定 ID，不存签名链接、临时预览链接或凭据。

## 多设备与同步

- 记忆内容不带任何设备特征：没有设备字段，文件名不含设备名，配置不登记设备。
- 每台机器只采集自己能读到的来源。
- 同步方式由用户选：同步盘、GitHub 私有仓库，或者不同步。插件不提供同步。
- 设计保证：
  - 新文件不重名，靠文件名里的随机串；
  - 除配置外，只有整理修改已有文件；
  - 整理前后各同步一次，同一时间只在一处整理；
  - 同步冲突副本由整理处理：当日文件的两节都保留，其他文件合并后再删除副本，删除前需用户确认。
- 记忆库放到 GitHub 时用私有仓库。只属于某台机器的绝对路径会暴露本地目录结构，在私有仓库内可以接受。

## 命名依据

动作名称都是动词：设置负责范围和来源，记录接收当前对话，采集读取既有资料，整理维护已有结果，调取只读回答。检查是对应动作的只读方式；更正和忘记属于整理，不另拆近义技能。被动和主动说的是信息从哪来，不等于手动和自动。

文件名称都是结果：入口、记忆、近况、事件、当日、积压、撤回，各回答一个问题。近况吸收了研究阶段对 Awareness 的讨论，但不用容易被理解成人格或隐式推理的"意识"。根作用域叫 `personal` 而不是 `global`，避免误解为组织共同规则。

## 人机协作与经验

平台负责执行、权限、人工决策和审计，XMemory 保留必要的结果和来源。接受、修改、驳回或转专家是事件，不是自动晋升经验的标签。经验需要条件、处理、已观察结果和例外；可执行的整套方法交给业务 Skill 维护，记忆只保存入口和非显然的例外。

组织经验需要额外的维护主体、审阅和权限；个人范围标签不能充当访问控制。本版不建设企业平台，也不自动发布组织规则。

## 纯技能边界

插件载荷只有 Markdown、TOML 示例、JSON 清单和许可证，没有运行期脚本、MCP、Hook、数据库、向量索引或定时器。因此不提供程序级并发保证、跨文件事务、来源适配器、自动同步或触发率承诺。这些边界靠"采集只新建、整理单点修改、写前确认、当日文件记账"来降低风险，而不是假装已经解决。

仓库里的检查和打包工具只在开发交付时使用，不进入插件载荷。

## 研究与正式产品的关系

`local/xmemory/` 是研究 demo，用来讨论来源只读、条件与来源、未完成项保留、按需读取和撤回等设计，不是正式旧版，也不提供升级链。

正式版本线：1.0.0 确立五技能、同构项目目录和 `personal` 作用域；1.0.1 补齐三端包装和技能资源自包含；1.0.2 统一用户级 `~/.agents/memory/` 集中存储；1.1.0 引入两层结构、事件文件与当日文件、分级整理、四类地址、读取协议和定时提示词。研究资料保持原样，只有用户明确需要复用时，才按 [已有资料接入](existing-data.md) 处理。
