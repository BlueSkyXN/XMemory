# 从足迹到经验

经验不是成功次数，也不是把一次反馈换成一句规则。它应该帮助下一次在相似条件下选择做法，并知道什么时候不适用。

## 提炼时问五件事

1. 当时要解决什么问题，有哪些条件和限制？
2. 实际采取了什么做法，为什么这么选？
3. 人工接受、修改、驳回或转专家的理由是什么？没有反馈就不编造。
4. 已观察到什么结果，什么仍未验证？
5. 下次哪些条件相同时可以参考，有什么例外或反例？

接受可能只代表允许继续；修改可能是需求变了；驳回可能只是证据不足；转专家可能本来就是权限边界。不要从一个按钮推导“事实正确”或“方法失败”。

## 选择落点

| 内容 | 落点 |
|---|---|
| 一次事件和反馈 | 足迹，并在当天每日记忆中概括 |
| 当前任务要继续处理的问题 | 意识的“待处理” |
| 有依据、可复用、带条件的判断 | 主题，`type` 为“经验”或“坑”，必要时设 `review` 复查日期 |
| 可重复执行的一整套方法 | 意识“记忆候选”中写“建议做成技能”和入口；XMemory 不自动创建或修改技能 |

例：代码修改和单元测试通过，但尚未部署。足迹记录本次阶段，意识保留“验证部署”；只有适用范围明确时，才提炼“汇报时区分实现、测试、部署和验收”这条经验。已有正式规范时引用规范，不再维护一份流程正文。

晋升经验要满足 [整理细则](curation.md) 的晋升条件：手动整理可以直接做；定时整理只写进意识的“记忆候选”。

## 复用与修正

一次失败也可以支持范围明确的反例；一次成功不能证明所有场景有效。不规定必须累计几次才算经验，依据应与主张范围相称。

后续复用的结果与原经验不符时，先检查条件、来源和执行差异，再补例外、更正或撤回；不要为了“持续进化”只积累正例。用户问是否更有效时，需要实际任务效果的证据，不能用记忆条数增长代替。

个人经验成为组织标准，需要额外的维护主体、审阅、权限与发布机制；本插件不自动做这种晋升。
